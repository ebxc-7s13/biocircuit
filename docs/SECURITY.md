## Boundaries and tested controls

- Managed Auth owns phone control and sessions. Academic membership is a separate private application and reviewer decision; clients cannot write role, membership or confirmation flags.
- Every exposed application table has RLS. Client DML grants are revoked. Invoker reads retain RLS; privileged functions fix search_path and authorize actual auth.uid(), role, eligibility, suspension and object access before mutations.
- Negative PostgreSQL tests cover anonymous/pending/member/owner/other/reviewer/moderator/admin, guessed private post/project IDs, revoked project membership, symmetric blocks, self votes, duplicate requests, private academic records, restricted reviewers, bounds and moderation appeals. Storage upload policies remain absent; unvalidated direct uploads fail closed.
- Private project logs are protected from unauthorized moderators as well as members. Authors may read their own moderated records and scoped decision reasons to appeal. Restoration does not silently restore reputation.
- Academic reviewers do not inherit moderation queues; metadata editors do not inherit academic records. Roles require trusted administrator assignment. Audits cannot be directly written or modified by clients.
- SQL accesses use parameterized SDK/RPC calls and constrained payloads. No user-controlled dynamic SQL or HTML execution is used. React renders text, source links require HTTPS without embedded credentials, and arbitrary source URLs are never fetched by the server.
- Publishing, replies, reporting, collaborations, review/administrative operations, scholarly search, avatars and general interactions have database budgets. Managed Auth/CAPTCHA provides pre-auth/IP controls. Provider requests have a shared transactional reservation budget and bounded caching/pages.
- Contribution events are unique and derived; self interactions are rejected. Recipient locks and pair/daily limits reduce award farming. Deletion, reopening and moderation invalidate awards. General multi-account/collusion detection still requires operational review.
- Edge Functions verify current Auth users, have an exact CORS origin, reject oversized streamed bodies even with spoofed lengths, use generic errors and no-store responses, and keep privileged clients entirely server-side.
- Processed avatars accept PNG/JPEG only, check extension/MIME/signature, decode pixels, limit size/pixels/time/concurrency, strip metadata and re-encode WebP. Private records gate 60-second signed reads; uploads are randomized and originals are not stored.
- Project images use a bounded PNG/JPEG decode/re-encode pipeline, private member-only records, 60-second links and commit-time membership/path checks. Known deleted objects enter a service-only cleanup queue; Storage cleanup scheduling and live object lifecycle checks remain external. Since migration 21 the private buckets refuse documents at the Storage layer too: `project-files` accepts only processor-encoded `image/png`, `academic-evidence` only PNG/JPEG (and has no ingestion path).
- Credential evidence and PDF/project documents are disabled. Magic-byte helpers are only a first gate, not proof of a safe PDF/image. No scanner or private evidence access workflow is represented as complete.
- CSP blocks object embedding, framing and unsafe script origins. Security/header files are deployment preparation; actual hosted headers, custom domains and CORS must be tested after deployment. Limited inline style permission supports the animation/UI library; unsafe inline scripts are not permitted.
- Browser token persistence uses the managed SDK. CSRF-sensitive cookie endpoints are not implemented; APIs use bearer authentication. XSS remains a critical session threat, so no unsafe HTML or arbitrary scripts are accepted.
- Build-time public environment names are allow-listed and privileged keys refused without logging their values. Bundle scans inspect emitted JavaScript/CSS for known privileged-key/private-key patterns. These pattern checks do not guarantee discovery of every possible secret.
- Account export uses the current UID only and includes private academic details and personal interactions without cross-account parameters. Deletion is authenticated, explicit, protects owned projects and cleans bounded Storage before removing identity.

## Privacy design

Collect degree pathway, institution, result state, year and minimal profile fields. Marks are optional, privately stored and never ranking inputs. Phone numbers remain in Auth. Evidence upload is off. No private content is sent to an AI/embedding provider, no analytics/session replay is enabled, and no global grade/prestige leaderboard exists. Public content, academic applications and personal interactions follow distinct policies.

Consent and patient-data/IP warnings are visible in onboarding/composer/policies. This does not establish that clinical data cannot be typed into a text field; reporting, moderation and an operator response process are still needed. Retention schedules, legal policies and private service configuration must be completed before launch.
